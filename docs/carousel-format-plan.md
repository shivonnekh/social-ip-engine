## PART 0 — Executive Summary

Carousels already work end-to-end *as a one-off*: `src/channels/ig_publish_carousel.py` is proven against a real live post, and `scripts/gen_carousel_pressure_points.py` proves the shared-brand-style generation approach. What's missing is everything *between* them: Notion authoring, per-panel generation into a Production row, an idempotency ledger, and a dashboard view.

This plan adds a **parallel deliverable track** inside the existing Content×IP Production row — the same way Cover Photo and DM Infographic are already parallel deliverables — plus a **separate, ledger-guarded publish state machine** so a carousel can go live on its own schedule without touching the Reel's (working, irreversible) publish path.

Net new surface: 3 studio scripts, 3 `src/` modules, 4 Notion properties, 0 new HTTP endpoints, 0 new Notion Automations.

## PART 1 — PRD

### 1.1 Problem

A Content Library concept today produces exactly one publishable artifact per IP: a Reel. Carousels are a proven, high-performing format for the "quick win" educational content this factory makes (the pressure-points carousel is live on @jackiechan.tcm), but producing one requires hand-writing a bespoke `scripts/gen_*.py`, hand-committing PNGs, hand-deploying, and hand-running a publish script with `--confirm-publish`. That is not repeatable and it bypasses every safety rail the Reels path has.

### 1.2 Goals

| # | Goal | Measure of success |
|---|---|---|
| G1 | Author a carousel in Notion the same way a video is authored | A Carousel Guide on the Content page produces per-panel prompts on every fanned-out row, with no hand-editing of production prompts |
| G2 | Generate N square panels per row with one command / one click | `generate_carousel.py --content "X"` fills every row's panel toggles at 1024×1024 |
| G3 | Publish a carousel live with the same paranoia as a Reel | Ledger-guarded, resumable, kill-switched, confirm-gated; a re-run publishes nothing |
| G4 | Review carousels in AI-IP Studio, not Notion | Panel filmstrip + regen-one-panel + publish gate in the row detail view |
| G5 | Independent scheduling from the Reel | A row can publish its Reel today and its carousel Thursday |

### 1.3 Non-goals (explicitly out of scope)

- **Facebook carousel mirroring.** FB's multi-photo post uses a different API shape (`/photos` with `published=false` + `attached_media`), not `ig_publish_carousel`. `notion_publish_fb_runner.py` stays Reels-only.
- **A deterministic pixel-template renderer** (PIL / HTML-to-image). Product decision #3 — keep gpt-image-2 + shared style block.
- **Video panels / mixed-media carousels.** Meta allows video children; we do images only.
- **Auto-deciding which concepts get a carousel.** A human writes a Carousel Guide or doesn't.
- **Retro-fitting existing published rows.** Rows already at `✅ Published` are not backfilled with carousels.

### 1.4 Product constraints (given, not re-litigated)

1. Panel count is variable per concept (2–10, Meta's own bound, enforced in `ig_publish_carousel.create_carousel_container`).
2. A concept can have both a Video treatment and a Carousel treatment; they are separate posts.
3. Panels are generated by `gpt-image-2` with a shared brand-style block appended per panel.
4. 1024×1024 square, mandatory.
5. Sequencing: schema + generation → publish wiring → dashboard.

### 1.5 Users / flows

**Shivonne (author):** writes a `🎠 Carousel Guide` on the Content page → fan-out → reviews the drafted panel prompts → clicks generate → reviews the filmstrip → regenerates panel 3 with an instruction → flips `🎠 Carousel Stage` to Published → post goes live.

**Claude/agent (operator):** runs the same scripts headlessly for batch work.

## PART 2 — Architecture

### 2.1 THE OPEN QUESTION, DECIDED

> Should a Production Tracker row fork by `Format` (Content × IP × Format), or should Carousel Panels be an additional section within the SAME Content × IP row?

**Decision: same row, additional section — Option B — with ONE addition: the carousel gets its own tiny publish state machine (`🎠 Carousel Stage`) on that row, rather than sharing the Reel's `Stage`.**

This is the user's lean, but it needs the publish-state amendment to actually work, and Option A has two concrete breakages worth documenting.

#### Option A — fork rows by Format (Content × IP × Format)

**Pros**
- One row = one post. Every existing per-row concept (Stage, Publish Date, ledger key = `row_id`, `🏷️ Title`, dashboard `next_action`, queue grouping) works unchanged.
- Carousel-only concepts are natural — no "row with no shots" edge case.
- Truly independent scheduling for free.

**Cons — two are concrete code breakages, not preferences:**
1. **`notion_fanout.existing_pairs()` dedups by IP page id alone** within a content (`studio/scripts/notion_fanout.py:130-137`). A second row for Jackie under the same concept is seen as "already linked" and silently skipped. Fan-out would need a Format-aware dedup key — i.e. the fan-out model *does* fork, which is the thing we're trying to avoid.
2. **Duplicate DM-keyword drafting.** `src/notion_sync.py` drafts a comment→DM keyword rule per row at `🟢 Ready to Publish`. Two rows for the same concept×IP share the same CTA keyword → two rules for the same keyword on the same account in `comment_responses.json`. Per `comment_rules.py`, first match wins, so the second is dead weight at best and a divergence risk at worst (edit one, the other still exists). The array format tolerates a duplicate keyword *across accounts*, not within one.
3. `apply_shot_plan()` would run on a carousel row and return `no-storyboard`, or worse build a video body on it — it needs Format-awareness anyway.
4. Doubles the workbench queue length and doubles `draft_title()` LLM calls per concept.

#### Option B — additional section in the same row

**Pros**
- **Exact existing precedent.** `apply_shot_plan()` already appends two non-shot deliverable sections after the shots (`cover_dm_blocks()`, `notion_prompts.py:691-715`). Each is: `heading_3` + bold label + code-block prompt + empty "drop it here" toggle. A carousel section is the same shape, N times. `generate_infographic.py` is already the working template for "generate the image for one non-shot section of a row."
- No fan-out change, no dedup breakage, one DM rule per concept×IP (and the carousel's closing-panel "comment PRESSURE" CTA is automatically covered by the row's existing DM wiring — the `dm_wired` chip already means the right thing).
- One row = "the Jackie version of this idea," which is already how the row behaves (it holds shots, a merged video, a cover, a DM infographic — four deliverables). A carousel is the fifth.
- The dashboard's row-detail view is already a multi-deliverable panel with per-section action buttons.

**Cons (and mitigations)**
- **A single `Stage` can't express "Reel live, carousel not yet."** → Mitigated by `🎠 Carousel Stage`, a *second, independent* select. Critically this leaves the existing `Stage` semantics **completely untouched**, so zero risk is introduced to the live Reels path.
- **`apply_shot_plan(rebuild=True)` is destructive** — it wipes the whole body including any uploaded panels. → The carousel builder is append-only + idempotent (`backfill_cover_dm_prompts.py` is the established precedent for exactly this), and `apply_shot_plan` re-appends the carousel *prompts* on rebuild so a rebuilt row isn't left carousel-less.
- **Carousel-only concepts** (no shots) hit `apply_shot_plan → "no-storyboard"` and the dashboard shows `next_action: fan_out` forever. → `_next_action_detail()` gains a carousel branch; a row with a Carousel Guide and no Shot Guide is a valid state.
- Longer row body → more Notion calls in `state.row_detail()`'s toggle-resolution pool. → Already parallelised (`ThreadPoolExecutor(max_workers=4)`), just more items.

#### Why the amendment (`🎠 Carousel Stage`) is not "forking the Stage model"

The `/admin/notion-publish` endpoint does **not** trust or read the webhook body — it re-scans the whole `prod_db` (`notion_publish._plan_publishes_locked`). The Notion Automation is only a "wake up" nudge. And per `notion_publish_scheduler._interval_seconds()`'s docstring (2026-07-21 root cause), **that Automation was found not to fire reliably in production at all**, which is why interval-mode polling exists. So:

- The carousel planner rides the **same endpoint and the same sweep**. No new endpoint. No new Notion Automation required (optional, if you want instant publishing).
- `🎠 Carousel Stage` is read by exactly one new planner. It never touches `Stage`.

**Recommendation: Option B + `🎠 Carousel Stage`.**

**What would change this decision:** if carousels ever need a *different IP set* than the Reel (e.g. carousel for Jackie only, Reel for both), or a *different CTA keyword* than the Reel, fork to Option A — at that point the row stops being one creative unit and the section model breaks down.

| Property | Type | Purpose | Env override |
|---|---|---|---|
| `🎠 Carousel` | checkbox | Generation done — all panels have images. Mirrors `🎨 Image` / `🎙️ Voice`. Ticked by `notion_carousel_image.py`. | — |

### 2.5 Key design decisions with rationale

**D1 — Panel prompts are FULLY COMPOSED in Notion (brief + style), not assembled at generation time.**
`studio/CLAUDE.md`'s core invariant is "the Shot Guide is the single source of truth… don't hand-edit the production prompts," and the corollary is that what's in the row's code block is *exactly* what goes to the model. Splitting the style out at generation time would break "what you see in Notion is what gets generated," and would silently change every already-generated panel's provenance the day someone edits the default. Cost: the composed prompt is long → see D2. Style edits are re-applied by re-running `apply_carousel_plan --force` on the row, the same contract as `apply_shot_plan`.

**D2 — `_rt_chunked()` is mandatory, not nice-to-have.**
Measured against the proven precedent: `_BRAND_STYLE` in `gen_carousel_pressure_points.py` is ~715 chars; the `slide-2-hegu` brief is ~1,140. Composed = **~1,855 chars, or 93% of Notion's 2,000-char-per-rich-text-item ceiling** — before we add the "N of M · swipe →" footer, the language clause, or a `【手动补充指令 via Studio】` appendix from the dashboard. This *will* break. `notion_prompts._rt()` (line 184) and `_code_block()` (686) do not chunk; `apply_script_property` truncates at `[:2000]`; only `state.append_shot_instruction` (line 442) and `regenerate_all_covers.py` (line 84) chunk at 1900. This has already caused a real incident on jimeng shot prompts. Fix it once, in `notion_prompts`, and reuse.

**D3 — Panel images are RE-HOSTED before being handed to Meta, not passed as Notion signed URLs.**
Notion file URLs are presigned S3 links that expire in ~1 hour. `notion_publish_fb_runner._refresh_video_url`'s docstring documents the exact incident this causes (2026-07-09/10, 4 rows failed 3× each with `FileUrlProcessingError … 403 Forbidden`) because the mirror structurally ran later than the URL's lifetime. A carousel resume after a Render deploy is the same shape. `notion_publish_media.resolve_cover` already solves this for covers by downloading + re-serving from `/media/covers/` — we copy that, into `/media/carousel/rows/<row_id>/`. It also reuses `_is_safe_download_url` (https-only) — required, since these URLs come from a Notion block a workspace editor could paste anything into and we re-serve the bytes publicly.

**D3a — On resume, re-hydrate missing local panel files before creating containers.** Render's disk is ephemeral. If the process restarted between claim and resume, `/media/carousel/rows/...` 404s. `_ensure_item_containers()` checks each file exists and re-downloads from Notion if not — but *only when it still needs to create containers*. Once an item container exists, Meta has already fetched the bytes and the URL is irrelevant.

**D4 — Aspect ratio is validated locally, on the actual bytes, right before the Meta call.**
The prompt says "square 1:1" and the generator requests `1024x1024`, but neither is a guarantee at the point of no return, and `ig_publish_carousel.py`'s docstring calls this out as the trap that already bit the first run. After download, read the PNG/JPEG header (stdlib `struct` on the IHDR / SOF marker — no Pillow dependency needed, matching this repo's stdlib-first habit in `notion_sync.py`) and refuse to claim the row if any panel's `width/height` falls outside `[0.8, 1.91]`. Report it in `skipped` with the offending panel and its actual dimensions. A rejected container is a wasted round-trip; a *silently* wrong-ratio panel is a failed publish that looks like a Meta outage.

**D5 — The carousel ledger is a SEPARATE FILE from the Reel ledger.**
`notion_publish.LedgerCorruptError`'s docstring calls treating a corrupt ledger as empty "the single worst possible failure mode for this feature" (mass re-post of every live row). The FB mirror got its own file for precisely this reason — "a bug anywhere in the new FB code could corrupt the one file protecting Instagram from duplicate posts." Identical reasoning: **no carousel code path ever opens `notion_publish_state.json` for writing.**

**D6 — Layer 2 of the duplicate guard is a PANEL-SET HASH, not a single URL.**
The Reel guard dedups on `video_url_stable`. A carousel has N URLs. Use `sha256` of the newline-joined, order-preserved, query-stripped panel URLs (`panel_set_hash`). Same semantics: a duplicated/recreated row pointing at the same image set is skipped permanently. Order is included deliberately — reordering panels is a genuinely different post.

**D7 — Carousel generation is its OWN orchestrator stage, not folded into `generate_assets.py`.**
Three reasons: (a) `generate_assets.py`'s docstring defines it by a specific human review checkpoint ("after you approve the Script → image + voice"); a carousel is a different artifact reviewed at a different time. (b) Folding it in spends gpt-image-2 credits on every concept, including ones with no Carousel Guide. (c) `pipeline_common.print_batch_summary` would report ❌ on a row whose *video* assets were fine — error isolation across formats matters. **But** `apply_carousel_plan()` *is* called from fan-out, so prompts always exist without a separate step, and `generate_assets.py` gains an optional `--with-carousel` passthrough for a genuine one-command run.

**D8 — Kill switch defaults OFF.**
`NOTION_PUBLISH_CAROUSEL_ENABLED=false` by default, matching `NOTION_PUBLISH_FB_ENABLED` and `NOTION_PUBLISH_SCHEDULE_ENABLED`. Rationale, quoted from the latter: "this sweep can create a brand new, real, irreversible Instagram post, so it should be opted into deliberately, not enabled for free on the next deploy." Also: it must be `sync: false` in `render.yaml` if it ever gets a dashboard value — see the `IG_ENABLED` multi-day outage note in the root `CLAUDE.md`.

**D9 — Poll budget is minutes, not 15 minutes.**
Images finish near-instantly (the proven ad-hoc script uses 3s × 20 = ~1 min). Default `IG_PUBLISH_CAROUSEL_POLL_MAX_S=180`, interval 5s — vs Reels' 900s. A carousel stuck for 3 minutes is broken, not slow.

**D10 — Poll the PARENT container only.**
`publish_pressure_points_carousel.py` proves this works and it's what Meta documents. Item containers are created and immediately referenced; a bad item surfaces as a parent-container error. Don't add N extra poll loops.

## PART 5 — Risks & Gotchas

### R1 — Aspect-ratio trap (HIGH likelihood, HIGH cost, already bit this repo once)
Meta accepts only 0.8–1.91. `gpt-image-2` offers 1024×1024 / 1024×1536 / 1536×1024, and the DM-infographic convention already in this codebase (`notion_infographic_gen._DEFAULT_SIZE = "1024x1536"`, ratio 0.667) is **outside** the range. Copying `generate_infographic.py` without changing `_SIZE` reproduces the bug exactly.
**Mitigations:** (a) `SIZE = "1024x1024"` as a module constant with a comment pointing at `ig_publish_carousel.py`'s docstring; (b) the composed prompt always states square 1:1; (c) **byte-level validation before any Meta call** (D4); (d) a unit test that fails if the size constant changes.

### R2 — Duplicate live post (LOW likelihood, CATASTROPHIC cost)
Irreversible; correcting one requires delete+republish, which this codebase has needed exactly once and treats as an emergency.
**Mitigations:** the full 3-layer ledger ported line-for-line; separate ledger file (D5); `_RUNNING_ROW_IDS`; `NOTION_PUBLISH_CAROUSEL_ENABLED` default false; two-click dashboard confirm; `--confirm-publish` on the verifier; `LedgerCorruptError` fails loud, never open.

### R3 — Notion 2000-char code-block limit (HIGH likelihood — measured at 93% of ceiling today)
See D2 for the numbers. Without Phase 0, `apply_carousel_plan` will 400 on realistic content and, because blocks are PATCHed in pages of 25, take the whole section's write down with it.
**Mitigation:** Phase 0.2 is a hard prerequisite for Phase 1, plus an explicit `len(prompt) > 1900` chunking test.

### R4 — Notion signed-URL expiry (MEDIUM likelihood, MEDIUM cost — this exact class already caused a 4-row × 3-attempt failure)
See D3/D3a.
**Mitigation:** re-host + re-hydrate-on-resume.

### R5 — `apply_shot_plan(rebuild=True)` destroys panels (MEDIUM likelihood, MEDIUM cost)
It calls `_wipe_all(row_id)` — the whole body, including uploaded images and audio. Putting carousels in the same row widens this blast radius.
**Mitigations:** `apply_carousel_plan` is append-only by default; `apply_shot_plan` re-appends carousel prompts after a rebuild; the existing warning in `studio/CLAUDE.md` (line 70) gets a carousel clause; the dashboard never exposes a rebuild button.

### R6 — Panel ordering / holes (MEDIUM likelihood, HIGH cost)
A 5-panel carousel silently posted as 4 panels — or with the closing CTA panel second — is a live, wrong, irreversible post.
**Mitigations:** ordering is strictly Notion block order; a missing image is a hard skip with a legible reason, never a compaction; the panel-set hash includes order so a reorder is treated as new content; the dashboard filmstrip renders in the same order and shows explicit "还没生成" placeholders.

### R7 — gpt-image-2 text rendering (MEDIUM likelihood, LOW-MEDIUM cost)
`notion_prompts` already documents that emoji render as tofu (`_strip_emoji`, added after the 2026-07-14 PIL-overlay fix), and that small in-scene dialogue text garbles — while `build_cover_prompt`'s rewrite proves **short, large, high-contrast text renders well**. Carousel panels sit in the "works" bucket only if the copy stays short.
**Mitigations:** run `_strip_emoji` over any `✏️` copy before composition; the prompt template asks for short label-style text with generous margins; the guide's authoring convention is "labels and one-liners, not paragraphs"; the closing-panel CTA keyword is the one string that must render legibly — verify it every time.

### R8 — CTA keyword coupling (LOW likelihood with Option B, HIGH cost)
Per root `CLAUDE.md`: "a caption CTA and a comment rule are two separate things that must be added together, or the CTA is silently dead." A carousel closing panel saying "comment PRESSURE" is dead unless a rule exists.
**Why Option B helps:** the carousel shares the row's Content relation and therefore its CTA and its single DM rule. The existing `dm_wired` gate (already required by `canPublish`) is reused by `canPublishCarousel`, so the carousel inherits the same protection for free. **Under Option A this would have been a new, separate failure mode.**

### R9 — Cost blowout (MEDIUM likelihood, LOW-MEDIUM cost)
M panels × N IPs × concepts of gpt-image-2 calls. A batch `--content` run over 2 IPs × 8 panels is 16 image generations.
**Mitigation:** `NOTION_CAROUSEL_MAX_GENERATIONS` cap per run, mirroring `NOTION_PUBLISH_MAX_COVER_GENERATIONS`; `--dry-run` prints the plan and cost shape; skip-if-present is the default (`--force` required to overwrite).

### R10 — Meta rate limits (LOW likelihood)
Instagram allows ~25 published posts per 24h per account, shared across Reels and carousels. A bulk Stage edit could bump it.
**Mitigation:** the existing attempt cap turns repeated rate-limit failures into a permanent `skipped` rather than an infinite hammer; log the Graph error verbatim so a 429/limit error is recognizable.

### R11 — Carousel-only rows confuse the workbench (MEDIUM likelihood, LOW cost)
A concept with no Shot Guide produces a row where `apply_shot_plan` returns `no-storyboard` and `next_action` sticks at `fan_out`.
**Mitigation:** Phase 3.3. Until Phase 3 lands, treat carousel-only concepts as a known Phase-1/2 limitation — every Phase-1 test concept should have both a Shot Guide and a Carousel Guide.

### R12 — Ephemeral Render disk vs. re-hosted panels (LOW likelihood, MEDIUM cost)
Covered by D3a. Worth an explicit test: delete the local panel files, then run resume, and assert the containers still get created.

### R13 — `render.yaml` blueprint-sync overwrite (LOW likelihood, HIGH cost — precedent exists)
The `IG_ENABLED` incident (5 deploys in one day silently re-disabling the live bot). Any carousel env var given a literal `value:` in `render.yaml` will be re-applied on every deploy, overwriting the dashboard.
**Mitigation:** `NOTION_PUBLISH_CAROUSEL_ENABLED` must be `sync: false`, and the "check the live state by observing behavior, not by reading git" habit applies — the planner's `{"enabled": false}` response shape in `/admin/notion-publish`'s JSON makes the live state directly observable, which is deliberate.
